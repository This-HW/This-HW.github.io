Marketing data platform rebuild

AMOREPACIFIC. Rebuilt pipelines spread across five environments into one traceable STG → ODS → DW flow

Context

I owned marketing data on AMOREPACIFIC's big data platform team. Data was supposed to flow STG → ODS → DW (data warehouse) → Mart, with the right processing at each stage.

Problem

  • In practice the stages were mixed with no rules.
  • Collection and loading ran in five separate places (a local Mac, AWS EC2, BigQuery, an ad-data platform and AWS Glue).
  • There was no visible lineage showing how a given table was produced, so tracing errors took a long time.
  • Duplicated storage and a broken snapshot design kept inflating the data.

What I builtled the first-stage rebuild, with help from colleagues

  • Moved collection into a shared module.
  • Reorganized the Snowflake data layers into a traceable STG → ODS → DW flow: raw data kept through ODS, transformations only in DW.
  • Built the MDP's Airflow DAGs myself so the whole flow is visible in one place.

What was still left, and how I fixed itsecond stage, on my own

  • With the flow cleaned up, reloading remained. Marketing data is often corrected after the fact, so the affected date range had to be deleted and reloaded: six manual steps across two systems.
  • Deleting data before the source arrived, or forgetting to restore a setting, could leave records missing or break the next day's batch.
  • I moved source extraction into Airflow, parameterized the date range, and added a check that skips downstream tasks when the source data is empty.

Result

Daily batch

over four hours→under ten minutes

Re-load

six steps→three

about 2.5 hours→30 minutes

  • The error-prone manual setting step is gone
  • Brought pipeline development and maintenance in-house from outsourced engineers, and retired BigQuery, EC2 and local servers from the flow.

Evidence

Internal documents can't be shared. I redrew the architecture myself, without internal system or table names.
